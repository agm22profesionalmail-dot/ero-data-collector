push a `main` (workflow `deploy-cloudflare.yml`) y **depende de las RPC

Orden de esta guía:

Todo lo que sigue se hace desde una copia local del repo con esta rama.

## 1. Backup previo — ANTES de tocar nada (fuera del repo)

Guardar en una carpeta local **fuera del repositorio** (por ejemplo
`~/edc-backup-20260927/`, nunca dentro del clon) el estado actual de lo que
esta migración reescribe. Con `psql` (`<CONN>` = cadena de conexión del
dashboard, rol postgres):

```sh
mkdir -p ~/edc-backup-20260927
# 1) jobs de pg_cron
psql "<CONN>" -c "select * from cron.job" > ~/edc-backup-20260927/cron_job.txt
# 2) definición de TODAS las admin_% y de artist_group
psql "<CONN>" -At -c "
  select pg_get_functiondef(p.oid) || E';\n'
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public'
     and (p.proname like 'admin\_%' escape '\' or p.proname = 'artist_group'
          or p.proname in ('artist_change_password', 'queue_artist_email', 'queue_artist_notice'))
   order by p.proname" > ~/edc-backup-20260927/functions_before.sql
# 3) dependencias de admin_check (y del resto de admin_%): qué objetos las usan
psql "<CONN>" -c "
  select p.proname, pg_get_function_identity_arguments(p.oid) as args,
         d.classid::regclass as dep_kind, d.objid, d.deptype,
         pg_describe_object(d.classid, d.objid, d.objsubid) as dependent
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
    left join pg_depend d on d.refobjid = p.oid and d.refclassid = 'pg_proc'::regclass
   where n.nspname = 'public' and p.proname like 'admin\_%' escape '\'
   order by 1, 2" > ~/edc-backup-20260927/admin_depend.txt
```

Sin `psql`: las mismas tres consultas en el SQL Editor y guardar la salida
(Download CSV) en esa carpeta.

Revisar `admin_depend.txt`: la migración `01` borra **todas** las
`admin_%(p_user text, p_pass text, …)` sin `CASCADE`. Las filas con
`dependent` distinto de vacío (y `deptype` `n`) son objetos —vistas,
políticas, triggers— que usan una firma antigua: la migración fallará en ese
DROP con un mensaje claro y hay que decidir a mano (recrear el objeto contra
la firma nueva o borrarlo) antes de repetir. Lo normal es que no haya
ninguna: las funciones plpgsql no crean dependencias entre sí.

Revisar también `functions_before.sql`: buscar `artist_change_password` y
apuntar si su cuerpo contiene `must_change_password = false` (se usa en el
paso 7.3).

### 7.3 `artist_change_password` cierra el primer acceso (decide si aplicar `04`)

`artist_change_password(p_current, p_new)` se creó a mano en producción (no
está en el repo). El flujo nuevo exige que al cambiar la clave ponga
`must_change_password = false`; si no, el artista se queda para siempre con
`{must_change_password: true, players: []}`.

Comprobar en SQL (o en el `functions_before.sql` del paso 1):

```sql
select pg_get_function_identity_arguments(p.oid) as args,
       pg_get_functiondef(p.oid) ~* 'must_change_password\s*=\s*false' as cierra_primer_acceso
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' and p.proname = 'artist_change_password';
```

- `cierra_primer_acceso = true` y `args = 'p_current text, p_new text'` →
  nada que hacer; **no** aplicar `04`.
- `false`, o 0 filas → aplicar
  `supabase/migrations/20260927_04_artist_change_password_guard.sql`. Es
  defensiva: vuelve a comprobar el cuerpo y solo sustituye la función si de
  verdad no pone `must_change_password = false` (si ya lo hace, `NOTICE` y no
  toca nada). La versión que instala identifica al artista igual que
  `artist_group` (cuenta Discord + bcrypt de la clave actual), exige ≥ 10
  caracteres y clave distinta, y escribe bcrypt.

Verificación funcional en cualquier caso: con el artista de prueba del
punto 7.2.4, tras cambiar la clave, `?panel` muestra las fichas y
`select must_change_password from public.artists where slug = '<slug>'` es
`false`.

## 9. Riesgos residuales documentados

### A3 — el panel de artistas muestra las opciones elegidas (riesgo aceptado)

`artist_group` v3 no entrega el fichero de configuración del personaje ni
los datos crudos (`player_type`, ids numéricos, `gear_*`, `weapon_main`,
`anim_name`): entrega imágenes resueltas y nombres. Pero el panel **muestra
las opciones elegidas** —especie, tono de piel y ojos, peinado, cejas, cada
pieza de gear con su nombre oficial y variante, color de tinta—, y con
nombres e imágenes un artista podría reconstruir a mano un `PlayerConfig`
equivalente salvo el arma y la animación. Es inherente a la función del
panel (referencia visual para dibujar) y **no se rediseña**: el compromiso
es que no se entrega nada listo para usar ni se puede descargar, y el
README lo describe así. Si en el futuro los renders se sirven completos
desde el servidor, la ficha puede dejar de mostrar las piezas por separado.

Las rutas de imagen siguen llevando el identificador interno de cada pieza
(`Hed_XXX`, `Har_SQD001`, …) porque el panel las pinta desde el CDN público
de Flexlion; con el RSDB público podría rehacerse el mapeo a los ids
numéricos.
